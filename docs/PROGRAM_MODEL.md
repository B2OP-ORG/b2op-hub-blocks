# Program Model — b2op-hub-blocks v2

This document describes how user programs are structured, executed on the hub, and generated from the block editor. It covers block categories, the Python execution model, the version header contract, and the Hub API reference.

---

## Block categories

The toolbox exposes eight block categories. Each maps to a set of block definitions (`src/blocks/defs/`) and a matching Python code generator (`src/blocks/generators/`).

| Category | File | Description |
| --- | --- | --- |
| `hub` | `hub.ts` | Core hub controls: LED color, buttons, IMU, power off, exit |
| `motor` | `motor.ts` | Encoder motor: start/stop by power or speed, rotate by degrees |
| `sensor` | `sensor.ts` | Port device access: detect device type, read sensor values |
| `neopixel` | `neopixel.ts` | NeoPixel LED strip control via `hub.board` pins |
| `lvgl` | `lvgl.ts` | Basic LVGL UI widgets: screen, label, button, image |
| `raw` | `raw.ts` | `raw_python` escape hatch — inline arbitrary Python |
| `advanced_hub` | `advanced_hub.ts` | IMU vectors, accel/gyro, board pins, logging |
| `advanced_motor` | `advanced_motor.ts` | Advanced motor control, encoder readback |

Advanced categories (`advanced_hub`, `advanced_motor`) are hidden by default. Enabling `settings.showAdvanced` reveals them without any code change — blocks are pre-tagged `advanced: true` and `toolbox.ts` filters on that flag.

## How programs execute on the hub

`runner.py` on the hub receives a Python source file and calls `exec()` on it. There are no lifecycle decorators, no event loop managed by the IDE runtime, and no `@on("setup")` / `@on("loop")` hooks. The script runs top-to-bottom, exactly like a normal Python program.

```python
# b2op-hub-blocks v2.0.0

import hub, lpf2
from lpf2 import devices

# Setup: runs once at start
dev_a = hub.ports.A.device()
if not isinstance(dev_a, devices.motor):
    raise TypeError("Port A: expected motor")

# Main loop: use while True for continuous behavior
while True:
    dev_a.startPower(50)
    time.sleep(0.1)
```

## when_program_starts hat

All blocks under the **"when program starts"** hat are emitted as top-level statements in the generated Python. There is no wrapper function. Statements are emitted in order.

Use `controls_whileUntil` (while True) inside the hat for continuous loops.

---

## Button callbacks

Button handler hats (`on button X pressed`) become `@hub.buttons.on()` decorated functions, emitted before the main body:

```python
@hub.buttons.on("center")
def _on_btn_center():
    hub.exit()
```

The C firmware layer calls these automatically on rising edge — no polling needed.

## Version header

Every file generated by b2op-hub-blocks begins with:

```
# b2op-hub-blocks v2.0.0
```

`pythonToBlocks()` (used when switching from Python to Blocks mode) rejects any source that does not have this header on its first non-empty line, returning the whole source as a single `raw_python` block. This prevents garbage block output from externally-edited or old-format Python.

## Hub API reference

| Task | Python |
| --- | --- |
| Sleep | `time.sleep(seconds)` |
| Exit program | `hub.exit()` |
| LED color (named) | `hub.led.setColorIdx(lpf2.color.RED)` |
| LED color (RGB) | `hub.led.setColor(r, g, b)` |
| Button pressed? | `hub.buttons.center()` → bool |
| IMU pitch/yaw/roll | `hub.imu.pitch`, `hub.imu.yaw`, `hub.imu.roll` |
| Reset IMU | `hub.imu.reset()` |
| Power off | `hub.powerOff()` |

Full type stubs for `hub`, `lpf2`, `lvgl`, and MicroPython stdlib live in `src/editor/lsp/stubs/files/`. Refresh them with `npm run sync-stubs -- --src ../Lpf2-micropython` after any firmware stub change.

## Project file format

Project files use format `"b2op-hub-blocks"` and semantic version `"2.0.0"`. Old files with format `"b2op-hub-blocks"` are accepted by `parseProject()` but marked as stale — the UI shows a warning.

Settings fields added in v2 (`lspMode`, `lspRemoteUrl`, `showAdvanced`) are merged from `DEFAULT_SETTINGS` into older saves on load, so old projects open without errors.
